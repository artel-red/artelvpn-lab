# Тестовый стенд

Да, стенд необходим. Нужны три уровня, каждый со своей границей доказательств.

## L0: абстрактная модель — реализовано

`lab/filter_model.py` и `lab/scenarios/` моделируют решения по IP, SNI, транспорту, объёму передачи и полному отказу.
`research/controller-v0/` сравнивает алгоритмы на искусственных исходах. Тесты исполняются без сети.
Модель получает метаданные, а не разбирает настоящие TLS/QUIC-пакеты. Это не эмулятор ТСПУ.

## L1: изолированная передача пакетов — запланировано

Топология: тестовый клиент → управляемый фильтр → собственный тестовый сервер; отдельный канал измерений.
Linux VM или одноразовые network namespaces; отдельная внутренняя сеть, без production-маршрутов и ключей.
Настоящие TLS/QUIC и выбранные движки, netem для потерь/задержек, контролируемые адресные и именные правила, packet capture только синтетических нагрузок.
Можно использовать CensorLab после оценки его модели и доверия зависимостям: https://censorlab.cs.umass.edu/.
Не следует объявлять набор iptables-правил копией ТСПУ. Реализации парсеров и состояние фильтра могут отличаться.

Внешние PR никогда не выполняются на runner такого стенда. Внешний опыт сначала воспроизводится в одноразовой среде без секретов.

## L2: согласованные линии — запланировано

Независимые регионы/операторы/устройства, отдельные периоды подтверждённых белых списков, повторение во времени.
Участники и операционные адреса остаются вне публичного GitHub; публикуются проверенные агрегаты.
Настоящий первый запуск и получение конфигурации проверяются отдельно от reconnect с заранее выданным профилем.

Переход L0→L1→L2 требует отдельного Issue, плана данных, контроля нагрузки и независимого review.
